# Reusable Exactification Testcase Contract

This contract is the on-disk interface between a blind exactification agent,
an SDP testcase, and an independent verifier. It wraps the repository's proof
format; it does not define a competing one.

The authoritative rational model and certificate schemas are
[`verify/FORMAT.md`](../verify/FORMAT.md):
`exact-block-sdp-model-v1` and `exact-block-sdp-certificate-v1`. If this manual
and that file ever disagree about a model, certificate, rational spelling,
affine coefficient, PSD trace, or checker behavior, `verify/FORMAT.md` wins.

Normative words `MUST`, `MUST NOT`, `SHOULD`, and `MAY` have their usual
requirements meaning.

## 1. Canonical case layout

```text
testcases/<case-id>/
├── input/
│   ├── manifest.json
│   ├── model.json
│   ├── approximate_solution.json
│   ├── README.md
│   └── raw/                       # optional original SDP/solver files
├── construction/
│   └── prepare.*                  # optional reproducible input adapter
├── tools/                         # optional case-specific public tools
├── attempts/
│   └── <attempt-id>/              # generated by a blind run
└── oracle/                        # optional, never mounted in a blind run
    ├── expected.json
    └── certificate.json           # optional golden certificate
```

Existing imported cases MAY temporarily keep the public input files directly
under `testcases/<case-id>/`. A blind harness treats that directory as `input/`,
but new and migrated cases SHOULD use the canonical layout above.

Only the manual, the chosen case's public `input/`, `construction/`, and
`tools/`, and the repository verifier are copied into a blind workspace. The
harness MUST exclude:

- `oracle/`;
- every previous `attempts/` directory;
- published serialized certificates; and
- generated exact kernels or matrices not declared as public problem data.

The agent writes only `attempts/<attempt-id>/`. It MUST NOT modify public input,
the manifest, preparation code, or the verifier.

## 2. Common serialization rules

- JSON is RFC 8259. Duplicate keys, comments, `NaN`, and infinities are
  forbidden.
- Text is UTF-8 with LF line endings.
- Paths are relative to the directory containing `manifest.json`, use `/`, and
  MUST NOT contain `..`, an absolute prefix, a URI scheme, or a symlink escape.
- Exact rational spellings and all structural rules for proof models and
  certificates come exclusively from `verify/FORMAT.md`.
- Approximate decimals are JSON strings. They are numerical evidence, never
  exact coefficients.
- Immutable source/model/solver artifacts SHOULD have SHA-256 hashes in the
  manifest or a referenced provenance file. A blind run MUST record the hashes
  it actually consumed in `run.json`.
- Matrix indices in proof models are zero-based. Approximate solution matrices
  are full square matrices in the block order declared by their names.

## 3. Lightweight `manifest.json`

The testcase manifest is metadata and routing. It is not a proof certificate.
Its required fields are:

| Field | Type | Requirement |
| --- | --- | --- |
| `format` | string | Exactly `exactification-testcase-v1` |
| `id` | string | Stable slug matching the case directory |
| `title` | string | Human-readable title |
| `field` | string or object | `Q` for the current trusted rational path; see Section 10 for extensions |
| `model` | string | Path to the authoritative proof model |
| `approximate_solution` | string | Path to normalized numerical block matrices |
| `fixed_objective` | rational string or null | Public exact value to fix, or null for discovery |
| `solution_side` | string | `affine_psd_blocks` for version 1 |
| `blind_input_policy` | object | Explicit certificate/oracle exclusions |

Recommended optional fields are `source`, `hashes`, `features`, `claim`,
`workflow`, `commands`, and `notes`.

A minimal current manifest is:

```json
{
  "format": "exactification-testcase-v1",
  "id": "example-rational-face",
  "title": "Example singular rational block SDP",
  "field": "Q",
  "model": "model.json",
  "approximate_solution": "approximate_solution.json",
  "fixed_objective": null,
  "solution_side": "affine_psd_blocks",
  "blind_input_policy": {
    "exact_certificate_included": false,
    "oracle_paths_mounted": false
  },
  "features": [
    "rational",
    "rank_deficient",
    "objective_discovery"
  ]
}
```

Unknown metadata fields MAY be preserved by a runner, but they cannot alter the
meaning of the required fields. A manifest with another `format` is not a
version-1 testcase.

### Given versus discovered objective

- A non-null `fixed_objective` is public problem data. It reveals a scalar, not
  an exact matrix certificate. The agent adds this value as an exact affine
  equation during face discovery.
- A null `fixed_objective` requires the objective-discovery phase in the
  workflow manual. The expected exact value MUST NOT appear in public paths,
  filenames, verifier diagnostics, preparation scripts, or templates.
- `workflow.objective_fields` MAY restrict discovery to `Q` or list declared
  field hypotheses. It is not an oracle value.

### Optional claim metadata

```json
{
  "claim": {
    "required_status": "EXACT_SDP_CERTIFICATE",
    "certificate_role": "sdp_feasible_point",
    "bound_relation": "sdp_feasibility_only",
    "theorem_checker": null,
    "matching_witness_checker": null
  }
}
```

Allowed `required_status` values are:

- `EXACT_SDP_CERTIFICATE`;
- `RIGOROUS_PROBLEM_BOUND`; and
- `SHARP_OR_OPTIMAL`.

The bundled verifier establishes SDP feasibility, PSD, and exact objective
value. Therefore the default, when `claim` is absent, is
`EXACT_SDP_CERTIFICATE`. A higher status requires a separately invoked exact
theorem adapter and, for sharpness, a matching exact witness or a checked
zero-gap pair. A prose statement alone cannot raise the status.

Useful `bound_relation` values are:

- `sdp_feasibility_only`;
- `sdp_optimum_le_certificate_objective`;
- `sdp_optimum_ge_certificate_objective`;
- `problem_optimum_le_certificate_objective`;
- `problem_optimum_ge_certificate_objective`; and
- `zero_gap_exact_optimum`.

## 4. Exact model: use `exact-block-sdp-model-v1`

`model.json` MUST pass the parser described in `verify/FORMAT.md` and the
command

```sh
python -m verify check model.json certificate.json
```

once a certificate exists. In particular, the model contains exactly:

- `format: "exact-block-sdp-model-v1"`;
- named positive-size PSD blocks;
- named affine constraints with senses `eq`, `ge`, or `le`; and
- one affine objective with sense `maximize` or `minimize`.

The affine coordinates are the displayed upper-triangular entries of those
blocks. The coefficient on an entry multiplies it once. There is no implicit
factor of two, so a trace inner product uses twice the off-diagonal matrix
coefficient. This convention MUST be tested by every SDPA/source adapter.

Do not add descriptive or ring fields to the proof model: the verifier rejects
unknown fields. Put descriptions, coefficient-field metadata, and provenance
in `manifest.json` or `README.md`.

An imported source representation such as `.dat-s` is evidence and a
reproduction input, but it is not a substitute for the exact proof model. The
case MUST document which solver side was converted and how signs,
off-diagonal factors, scalar blocks, and the objective were mapped.

## 5. Normalized approximate solution

`approximate_solution.json` is exploratory input with this public schema:

```json
{
  "format": "approximate-block-sdp-solution-v1",
  "numeric_type": "decimal",
  "claimed_precision_bits": 512,
  "claimed_objective": "3.8400000000000000001e-2",
  "blocks": [
    {
      "name": "X",
      "matrix": [
        ["1.0", "0.5"],
        ["0.5", "0.25"]
      ]
    }
  ]
}
```

Requirements:

- `format` and `numeric_type` have exactly the values above.
- Exactly one of `claimed_precision_bits` and `claimed_precision_digits` is
  present and is a positive integer.
- `claimed_objective` and every matrix entry are decimal strings.
- There is exactly one named full square matrix for every model block and no
  extra matrix.
- Dimensions match the model and numerical matrices are symmetric to the
  precision claimed by the producer. Exact symmetry is not required here.
- The blind agent recomputes all affine residuals and spectra; it does not trust
  a claimed solver status or objective.

Multiple precision runs MAY be placed in `input/numerical/<run-id>/` and listed
in `workflow.additional_approximate_solutions`. The preferred file remains the
required `approximate_solution` path.

## 6. Exact candidate and certificate

The proof artifact MUST use `exact-block-sdp-certificate-v1` exactly as defined
in `verify/FORMAT.md`. It assigns:

- one full exact rational symmetric matrix to every named model block;
- the exact `claimed_objective`; and
- a complete `symmetric-schur-v1` PSD replay trace for every block.

The strict schema intentionally has no testcase ID, provenance, kernel, or
numerical fields. Put those in sibling attempt artifacts, never into
`certificate.json`.

During reconstruction the agent MAY first write `candidate.json` with the same
`format`, `claimed_objective`, and exact block matrices but without `psd_trace`.
The trusted emitter converts it to the complete certificate:

```sh
python -m verify emit-traces \
  input/model.json \
  attempts/<attempt-id>/candidate.json \
  -o attempts/<attempt-id>/certificate.json
```

The emitter failing to find a valid trace is an exact PSD failure, not a reason
to edit the verifier or skip a block.

## 7. Attempt directory

Every blind run writes a new immutable attempt:

```text
attempts/<attempt-id>/
├── run.json
├── objective-candidates.json
├── spectra.json
├── kernels.json
├── affine-system.json             # optional exact discovery system
├── candidate.json
├── certificate.json
├── verifier-output.json
├── verification.json
└── proof.md
```

### Discovery artifacts

`spectra.json` records scaled singular/eigenvalue clusters at every precision.
`kernels.json` records, for each block:

- candidate nullity and precision runs used;
- integer relation matrix and exact rank;
- exact kernel basis over the attempted field;
- relation height and normalized residual at each validation precision;
- number/rank of added matrix-times-kernel-vector equations; and
- provenance `numerical_lll`, `complementary_slackness`, or `mixed`.

These files explain how the certificate was found. The verifier does not trust
them.

### `run.json`

Record:

- UTC start/end timestamps and attempt ID;
- repository commit and dirty-worktree state;
- platform and tool/library versions;
- complete command argument arrays and exit codes;
- seeds;
- precision, relation-height, and denominator ladders;
- hashes of every consumed and generated file;
- all objective/nullity branches attempted; and
- whether a public matching construction was used.

Commands in manifests or run metadata SHOULD be JSON argument arrays. A runner
substitutes documented placeholders and invokes the program directly, without
shell interpretation.

### `verification.json`

This is the harness-level report, not a replacement proof schema. It records:

- case/attempt IDs and model/certificate hashes;
- the exact verifier command and exit code;
- parsed `--json` output from the bundled verifier;
- whether every model block and constraint was covered;
- theorem-adapter and matching-witness results, when required; and
- one final workflow status.

The raw bundled report is retained verbatim as `verifier-output.json`.

## 8. Exact verification protocol

Run from the repository root in a fresh process:

```sh
python -m verify emit-traces \
  testcases/<case-id>/input/model.json \
  testcases/<case-id>/attempts/<attempt-id>/candidate.json \
  -o testcases/<case-id>/attempts/<attempt-id>/certificate.json

python -m verify check \
  testcases/<case-id>/input/model.json \
  testcases/<case-id>/attempts/<attempt-id>/certificate.json \
  --json
```

The harness MUST require exit status zero. Per `verify/FORMAT.md`, status one is
an exact mathematical failure and status two is malformed input, I/O failure,
or command misuse.

The checker MUST remain candidate-independent. It verifies validity, not
equality to a golden matrix. It MUST NOT contain:

- a hidden expected certificate or target value in discovery mode;
- a certificate-byte hash whitelist;
- a numerical eigenvalue fallback;
- a skipped PSD block or affine constraint; or
- a "known good" bypass.

After the rational verifier passes, run any exact theorem and witness checkers
declared by `claim`. Without them, the final status is at most
`EXACT_SDP_CERTIFICATE`.

## 9. Blind harness protocol

For each case:

```text
1. Construct a clean workspace from the manual, repository verifier, and the
   case's public input/construction/tools only.
2. Confirm that oracle/, previous attempts/, and published exact matrices are
   absent, not merely unread by convention.
3. Start a fresh agent with only:
       Follow manual/EXACTIFICATION_WORKFLOW.md for this manifest.
4. Let the agent create one attempts/<attempt-id>/ directory.
5. Run the exact verifier in a fresh process and capture --json output.
6. Check output presence, hashes, model coverage, and required status.
7. Only now expose oracle/expected.json to the harness and compare declared
   postconditions such as exact objective or rank.
8. Archive the complete attempt. Never repair a failed blind attempt in place.
```

A testcase passes only when:

- its public input parses and hashes match;
- the bundled verifier exits zero on the generated exact certificate;
- its reported block and constraint counts equal the model counts;
- all additional checkers required for `claim.required_status` pass; and
- post-blind oracle conditions, if any, match.

Agreement with an oracle before exact verification is not a pass.

## 10. Field extensions and quadratic cases

The trusted `exact-block-sdp-*-v1` implementation is deliberately rational.
Therefore a manifest with `field: "Q"` uses the complete current proof path.

A future quadratic case MAY declare:

```json
{
  "field": {
    "kind": "Q_sqrt_d",
    "radicand": 2,
    "embedding": "positive_root"
  },
  "proof_format": "<versioned quadratic model/certificate format>",
  "verification_command": ["<exact quadratic checker>", "..."]
}
```

Such a case is an **extended testcase**, not a valid rational-v1 proof case. It
may exercise the quadratic discovery algorithm immediately, but it cannot
receive `EXACT_SDP_CERTIFICATE` until a versioned trusted checker provides:

- canonical exact \(a+b\sqrt d\) serialization;
- exact arithmetic and sign decisions in the selected real embedding;
- exact affine/objective checks; and
- a complete exact PSD proof for every block.

Never coerce quadratic coefficients into rational decimals or reuse the
rational format name. The absence of this checker is an implementation
dependency, not evidence that the DLM quadratic method fails.

## 11. Suite coverage

The mandatory rational validation suite MUST cover:

- a singular flag-algebra case with several kernel dimensions (the Grzesik
  pentagon SDP);
- a rational SDP generated from the DLM ancillary sources;
- a held-out rational face whose numerical basis/entries are irrationally
  rotated but whose kernel subspace is rational.

It SHOULD additionally cover a strictly feasible control and a negative
control that must not produce a false exact certificate within the declared
search limits.

Recommended feature tags are `rational`, `singular`, `flag_algebra`,
`packing_sdp`, `multiple_kernel_dimension`, `objective_given`,
`objective_discovery`, `strictly_feasible_control`, and
`negative_control_no_certificate_in_limits`.

Quadratic DLM cases SHOULD be included as extended discovery tests now and
promoted to mandatory proof tests only after the quadratic trusted checker in
Section 10 exists. This preserves the full methodology goal without pretending
that a rational-only verifier proves algebraic PSD.

The manual is demonstrated for the current v1 scope only when every mandatory
rational case passes from a clean blind workspace. Every included negative
control must also produce no false proof.

## 12. Status and failure contract

- `INPUT_INVALID`: manifest, hashes, proof model, dimensions, or provenance
  fail preflight.
- `EXPLORATION_ONLY`: numerical/kernel candidates exist but no complete exact
  certificate passes.
- `NO_CERTIFICATE_FOUND`: declared search limits were reached reproducibly;
  this is not a mathematical nonexistence result.
- `EXACT_SDP_CERTIFICATE`: the bundled exact checker accepts every rational
  block, constraint, and the objective value.
- `RIGOROUS_PROBLEM_BOUND`: the exact SDP certificate plus theorem adapter prove
  the declared original-problem bound.
- `SHARP_OR_OPTIMAL`: the previous checks plus a matching exact witness or
  checked zero-gap argument pass.

No other label is a successful result under this contract.

## 13. Provenance

Every non-synthetic case SHOULD link primary sources directly and record hashes
for downloaded archives, original solver inputs, generated proof models, and
numerical outputs. For the motivating methodology these include DLM's
[paper](https://doi.org/10.1137/20M1351692),
[arXiv record](https://arxiv.org/abs/2001.00256), and
[ancillary source archive](https://arxiv.org/src/2001.00256).

Manual transcription requires an independent generator or a
coefficient-by-coefficient comparison against the source. A solver result needs
the solver name/version, precision, tolerance, command, and hash. Provenance
establishes which SDP was certified; it never substitutes for exact checking.
